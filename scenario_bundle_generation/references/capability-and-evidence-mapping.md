# Capability and evidence mapping

Use the supplied public export to bind structural requirements and interpret
available interfaces. The export constrains what can be requested; it does not
determine which objectives or scenarios belong in the bundle.

## Copy identities from a verified export

Use Operator's `operator.dev/target-capability-manifest/v1alpha1` public export
and keep its generated source companion available for offline validation.
Read the matching
[capability contract](https://github.com/intrusiveai/operator_sandbox/blob/main/schemas/CAPABILITY_EXPORT_CONTRACT.md)
when checking an unfamiliar export.

Copy:

- `capabilities.target_id` to `target_requirements.target_id`;
- `source.capability_source_digest` to
  `target_requirements.capability_source_digest`;
- the export's `capability_projection_digest` only if exact static matching
  is requested or required by the user's stated compatibility constraint.

The source digest records authoring provenance. It is not a raw hash of the
public JSON and is not a requirement that a live session have the same source
digest. The companion is named from `source.raw_digest` and belongs to host
provenance, not bundle supporting artifacts. Preserve Operator's generated bytes;
do not calculate replacement capability identities or handwrite the companion.

Compatibility matching is the default: live admission checks the same logical
target and explicit dependencies under current policy. An exact projection pin
must match both the authoring export and live static projection. Do not add it
merely for apparent rigor, and do not remove an existing requested pin to make
validation pass. Healthy restore does not require rewriting the authored bundle.

If the export is missing, stale for a newly required capability, or unsupported,
obtain a fresh export through Operator management. Continue useful content
drafting, but do not claim a bound, ready bundle or invent missing identifiers.

## Use references with the correct meaning

| Namespace | Refers to |
| --- | --- |
| `operation:` | An advertised application operation |
| `action:` | An advertised action capability |
| `service:` | A logical service scope |
| `file_namespace:` | A logical mutable-file scope |
| `evidence:` | A feedback/evidence class |
| `feature:` | An advertised feature, such as snapshot support |

Copy actual references rather than constructing them from prose, array positions,
session IDs, or guessed names. `required_capability_refs` may use any supported
namespace; `guidance.action_refs` accepts only action references, and
`evidence.requested_classes` accepts only evidence references.

Requirements may be empty. An available capability is not a reason to require it.
A service/namespace reference asserts availability of that scope; it does not
promise an unstated endpoint, creation permission, field shape, or mutation.
Concrete operations remain subject to the host's per-attempt checks.

## Check delivery information and adapter differences

For an operation needed by the supplied content, inspect its `delivery_status`,
input encoding/media type, byte ceiling, and declared schema/examples. An operation
with `missing-input-contract` cannot satisfy a runnable-operation requirement.
Do not guess the missing input contract or an unknown output schema. Public
examples are descriptive data, not mandatory scenario contents.

Interceptor exports may describe services, files, actions, and snapshots, subject
to their individual constraints. An action family alone does not establish that
an arbitrary service or file is selectable.

HTTPS exports describe administrator-declared application operations and limited
feedback. They have no Interceptor action, service, file, or snapshot capabilities,
and unknown output structure stays unknown. Do not change a user-supplied scenario
to hide this mismatch; report the unavailable requirement or optional gap.
See [HTTPS targets](https://github.com/intrusiveai/operator_sandbox/blob/main/docs/HTTPS_TARGETS.md)
only when that adapter is relevant.

## Database-backed scenarios

When the user's scenario involves PostgreSQL, distinguish the requested mechanism:
`database_response` modifies eligible returned values; `environment_state` changes
permitted stored records. Bind only the actual action/service references and
policy limits in the public export. A database service does not imply arbitrary
SQL, writable fields, record creation, or an HTTP/MCP route. Preserve the export's
advertised selectors and supported placement types; do not invent a new bundle
field or reference namespace for a database table.

Initial schemas and populated/vector seeds belong in the Interceptor Blueprint,
not in a bundle as executable database setup. Supporting files remain passive
content. Describe delivery and outcome criteria separately when the supplied goal
requires them: rewritten or retrieved content does not itself prove model delivery,
and model delivery does not prove a committed business mutation. Independent
committed-state evidence must actually be available under the selected feedback
policy; administrator-only archives are not additional Harness feedback.

Express any user-required baseline/reset expectations using advertised snapshot
capabilities and campaign policy. Disabling a state injection does not reverse its
stored effects. These distinctions constrain compatibility and interpretation;
they do not prescribe database scenarios or expand the user's testing agenda.

## Required dependencies versus suggestions

Top-level required references and dependencies on required objectives/scenarios
must be available and usable. Missing required dependencies block readiness.
Optional-item dependencies produce recorded gaps and unavailable routes.

Action suggestions and requested evidence classes remain optional unless also
listed as explicit required dependencies, even on a required scenario. A wrong
reference namespace or dangling objective/artifact link is an error, not an
optional gap. Preserve unavailable references already supplied as optional;
do not invent new optional references to expand the bundle.

The public export describes capabilities, not administrator permission. Required
actions also need an allowed route; required evidence needs effective feedback
permission. Offline source checks do not establish these live conditions.

## Express feedback, evidence, and limits honestly

Use the requested feedback profile and evidence needs from the user's scope,
checking the export's supported profiles and each evidence class's availability.
Distinguish observations expected by the scenario from evidence the harness can
actually receive. Administrative post-run archives are not extra harness-visible
evidence classes.

If a required observation is unavailable, report that dependency; do not silently
reinterpret it or broaden host policy. Optional unavailable feedback belongs in
validation gaps and `evidence.limitations`, where appropriate. Do not equate missing
feedback with a negative result.

Requested feedback and budgets can only narrow installed permissions and ceilings.
Use the version-matched
[feedback contract](https://github.com/intrusiveai/operator_sandbox/blob/main/schemas/FEEDBACK_CONTRACT.md)
only when profile interactions matter. Do not change or restart an Interceptor
session just to request a narrower harness view.

Record requested settings as requested. Effective settings and runtime readiness
come from Operator admission; do not invent them from the bundle alone.
